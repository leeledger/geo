# 사이티드 에이전트 운영 설계

작성: 2026-09-16 · 설계 제안 · 아직 구현하거나 운영에 적용하지 않음

## 목표

고객의 AEO·GEO 목표를 이해하고, 지시가 없어도 문제와 기회를 발견하고, 원인을 조사하고, 권한 안에서 조치하고, 결과를 확인하는 조직을 만든다. 각 업무에는 끝까지 책임지는 담당자가 있다.

스킬은 업무 방법이다. 직원 역할은 목표·책임·권한·기억·업무함을 가진다. 한 직원이 상황에 맞는 여러 스킬을 선택한다. 스킬마다 별도 에이전트를 항상 실행할 필요는 없다.

## 현재 코드에서 확인한 출발점

- `academy/scripts/scout.mjs`: 규칙으로 이상을 탐지하고 `what/why/todo`를 반환한다. 원인 조사와 해결 실행은 맡지 않는다.
- `.github/workflows/scout.yml`: 정찰 결과를 이슈로 연결한다. 이슈가 탐지 목록에서 사라지는 것과 해결이 검증되는 것은 구분해야 한다.
- `academy/scripts/log-intervention.mjs`: 한 일·이유·기대 효과를 저장한다. 가설, 실행, 검증 결과를 하나의 문제에 연결할 기반으로 확장한다.
- `web/lib/brief-core.mjs`: 활동 기록을 집계한다. 해결 책임과 다음 검증 시각까지 확장한다.
- `academy/clients.mjs`와 `geo.clients`: 고객 정보가 나뉘어 있다. 신규 고객이 DB에만 있고 측정 설정에는 없는 상태를 탐지해야 한다.
- 일간·주간·발행 스킬과 기존 실행 스크립트를 재사용한다.

현재 판단에서 보완할 사례:

1. 크롤러 기록 0건으로 측정 장치 미설치를 단정할 수 없다. 설치 여부·수집기 상태·방문 부재를 각각 확인해야 한다.
2. 경쟁 검색어 최신 결과가 0이고 전체 측정일이 3일 이상이라고 해서 3일 연속 0인 것은 아니다. 연속 실패를 주장하려면 해당 날짜별 근거가 필요하다.
3. DB 조회 실패를 빈 배열이나 0으로 바꾸면 미측정과 정상 상태가 섞인다. 데이터 수집 실패를 별도 상태로 보존해야 한다.
4. 발행 주기나 네이버 이관 규칙은 해당 서비스를 계약한 고객에게만 적용해야 한다.

위 항목은 코드에서 확인한 설계상 한계이며, 현재 운영 장애가 발생했다는 뜻은 아니다.

## 고객별 업무 기준

착수할 때 고객별 운영 계약을 기록한다.

| 항목 | 내용 |
|---|---|
| 사업 목표 | 어떤 고객의 어떤 문의·구매를 늘릴 것인가 |
| 제공 업무 | 기술 개선, 콘텐츠, 유통, 측정 중 계약 범위 |
| 대상 | 도메인, 브랜드 식별 규칙, 시장·언어, 주요 질문, 경쟁사 |
| 성공 기준 | AI 언급·인용과 유효 문의 등 고객별 목표, 기준선, 평가 기간 |
| 측정 조건 | 엔진·질문 세트·반복 횟수·수집 방식·기간·측정 버전 |
| 작업 권한 | 수정 가능한 자산, 허용 작업, 배포·발행 절차, 담당 연락처 |
| 제약 | 금지 주장, 확인된 사실, 일정, 비용 한도, 접근 불가 항목 |

조회나 작업은 항상 `client_id`에 묶는다. 고객 설정 누락 시 다른 고객의 기본값을 사용하지 않는다. 기존 설정 파일은 초기에는 어댑터로 읽고, 검증 후 DB를 단일 원본으로 옮긴다.

성과는 기술 정상성 → 수집·색인 → 검색·AI 노출 → 유효 문의 → 계약·매출로 나누어 본다. 앞 단계 개선으로 뒤 단계 성과를 단정하지 않는다. AI 노출은 원문과 표본 수를 보존하고 동일 조건의 반복 측정으로 비교한다.

## 직원 역할

| 역할 | 책임 | 맡길 스킬 예시 | 완료 기준 |
|---|---|---|---|
| 고객 담당 PM | 고객 목표 이해, 우선순위, 업무 배정, 마감·성과 추적 | 착수 점검, 브리핑, 계획, 보고 | 모든 주요 문제에 담당자와 다음 행동이 있음 |
| 진단·분석 담당 | 데이터 신뢰성 확인, 가설 비교, 원인 범위 좁히기 | 검색·인용 측정, 로그·사이트 진단, 경쟁 지면 분석 | 근거와 불확실성을 담은 실행 가능한 진단 |
| 기술 담당 | 접근·색인·페이지 구조 문제 해결 | robots, sitemap, 구조화 데이터, 배포 점검 | 대상 자산에 반영됐고 기능 검증을 통과함 |
| 콘텐츠·유통 담당 | 고객 질문에 답하는 콘텐츠 제작과 배포 | 조사, 초안, 사실 확인, 도해, 발행, 이관 | 검토한 산출물이 대상 지면에 정상 반영됨 |
| 검증 담당 | 조치·부작용·후속 성과 확인 | 전후 비교, 독립 재조회, 회귀 점검 | 성공·실패·판정 유보를 근거로 기록함 |

초기에는 하나의 실행기가 역할별 문맥과 도구 권한을 바꿔 순차 수행한다. 동시 업무가 필요해질 때 작업자를 늘린다. 검증은 실행자의 설명만 재요약하지 않고 원본 상태를 다시 읽는다. Arch·Bob·Richard는 이 운영 시스템을 개발하는 역할이며 고객 업무 역할과 별개다.

## 문제를 처리하는 절차

1. 발견: 이상 신호, 신규 고객·콘텐츠, 예정된 업무, 고객 목표와의 격차로 업무를 만든다.
2. 사실 확인: 데이터의 신선도·측정 성공 여부·고객 범위·계약 적용 여부를 먼저 확인한다.
3. 문제 정의: 관측 사실, 기대 상태, 사업 영향, 아직 모르는 것을 구분한다.
4. 조사: 가능한 원인을 기록하고 구분할 수 있는 가장 저렴한 검사를 선택한다. 단순한 문제에 가설 수를 억지로 늘리지 않는다.
5. 계획: 조치 후보를 예상 효과·근거·비용·되돌릴 수 있는지로 비교한다. 조치 전에 검증 기준과 재확인 시각을 정한다.
6. 실행: 허용된 스킬로 수행하고 입력·출력·변경 전후·실행 식별자를 남긴다.
7. 검증: 즉시 확인 가능한 정상 반영과 시간이 필요한 노출·성과를 따로 확인한다.
8. 후속 처리: 해결, 추가 조사, 효과 관찰, 외부 대기로 이동한다. 재발하면 과거 업무와 연결한다.

원인을 완전히 확정하지 못해도 위험이 낮고 되돌릴 수 있는 실험은 가능하다. 가설과 성공 기준을 먼저 저장한다. 결과가 기대와 다르면 같은 작업을 반복하지 않고 가설을 갱신한다.

## 업무 상태와 책임

`발견 → 조사 중 → 실행 준비 → 실행 중 → 검증 중 → 해결`

추가 상태는 `효과 관찰`, `외부 대기`, `보류`, `해당 없음`이다. 일시적인 실행 오류는 시도 기록으로 남기고, 재시도 한도 이후에는 조사 또는 외부 대기로 전환한다.

- 업무마다 담당자 한 명을 둔다. 인계받은 담당자가 수락하기 전까지 기존 담당자가 책임진다.
- 해결 외 상태에는 `next_action`과 `next_check_at`을 둔다. 외부 대기에는 필요한 사람·정보·권한을 적는다.
- 탐지가 사라져도 근거 없이 해결하지 않는다. 데이터 조회 실패는 정상화가 아니다.
- 기술 수정 완료와 고객 성과 달성을 별도 목표로 연결한다. 색인 요청 접수를 AI 인용 개선으로 기록하지 않는다.
- 새 근거가 없으면 반복 분석하지 않는다. 재확인 일정까지 기다리며 독립적으로 가능한 업무를 진행한다.

## 저장할 데이터

| 테이블 제안 | 핵심 필드 |
|---|---|
| `client_operating_profiles` | client_id, 목표, 계약 범위, 자산·권한, 측정 설정, 예산, 버전 |
| `work_items` | client_id, 목표, 문제, owner, 상태, 우선순위 근거, 중복 키, next_action, next_check_at |
| `observations` | client_id, work_id, 출처, 측정 시각, 수집 성공 여부, 값, 원문 참조, 측정 버전 |
| `hypotheses` | work_id, 가설, 지지·반박 근거 참조, 구분 검사, 판단 상태 |
| `action_runs` | work_id, skill/version, 입력, 권한 판정, idempotency_key, 시작·종료, 결과, 비용, 롤백 참조 |
| `verifications` | work_id, action_id, 기준선, 성공 기준, 평가 시점, 재조회 근거, 판정 |
| `case_lessons` | 원인, 적용 조건, 효과 있었던 조치, 실패 조치, 근거, 검토 기한 |

상태 변경 이력은 추가 방식으로 보존한다. 기존 `interventions`는 실행 기록과 연결하고 과거 기록은 유지한다. 고객 원문과 개인정보는 고객 범위 안에 두며, 공통 학습에는 식별 정보를 제거한 절차만 남긴다.

## 실행기와 스킬의 연결

예약 실행 또는 이벤트 → 관측 수집 → 업무 생성·중복 병합 → PM 우선순위 결정 → 역할별 조사·계획 → 권한 검사 → 스킬 실행 → 별도 검증 → 재확인 예약.

LLM은 근거를 해석하고 다음 검사를 제안한다. 업무 상태 전이, 고객 범위, 권한, 재시도, 비용 한도는 프로그램이 검사한다. 모델이 만든 임의 셸 명령을 그대로 실행하지 않는다.

각 스킬에는 입력·출력 스키마, 필요한 도구, 부작용, 선행 조건, 성공 확인 방법, 시간 제한, 중복 실행 방지 방법을 정의한다. 기존 CLI는 어댑터로 감싸 구조화된 결과를 반환하게 한다. 출력은 `성공/실패/확인 불가`를 구별한다.

작업자는 DB에서 업무를 잠금과 만료 시각으로 확보한다. 프로세스가 죽으면 만료 뒤 복구하되, 외부 작업의 성공 여부가 불명확하면 먼저 실제 상태를 조회한다. 고객 자산과 브라우저 프로필을 공유하는 작업은 동시에 실행하지 않는다.

초기 운영 제안: 같은 일시 오류는 최대 2회 재시도, 업무당 한 실행 회차에서 조사 도구 최대 6회. 한도 도달 시 근거·미해결 질문을 저장하고 재계획한다. 유료 작업은 고객별 사전 설정 예산 안에서만 실행하며 금액을 임의로 정하지 않는다.

## 자율성과 권한

| 상황 | 처리 |
|---|---|
| 읽기·진단·초안·내부 보고 | 설정된 도구와 비용 범위에서 자동 진행 |
| 사전 허용된 수정·배포·발행 | 기존 검토 절차와 범위를 만족하면 자동 진행 |
| 고객 서버 접근권한·사실 확인 등이 부족함 | 조사 결과와 준비된 산출물을 보존하고 필요한 입력만 요청 |
| 새 비용·계약 변경·삭제·외부 메시지 발송 | 해당 행위에 대한 명시적 권한을 확인하고, 없으면 준비를 끝낸 뒤 요청 |

이미 받은 권한은 고객·자산·행위 범위와 유효 조건을 기록하여 반복해서 묻지 않는다. 웹페이지·고객 문서에 담긴 명령은 운영 권한으로 취급하지 않는다. 로그인 정보는 도구가 관리하고 모델 기록에는 넣지 않는다.

## 실제로 달라질 행동 예시

상황: 어떤 고객사의 AI 크롤러 기록이 36시간 동안 없다.

1. PM이 해당 고객의 측정 계약과 이전 방문 패턴을 확인하고 진단 담당에게 배정한다.
2. 진단 담당은 최근 수집 작업 성공 여부, 기록 장치 설정, 사이트 응답, robots 변경 이력을 확인한다.
3. 사이트 정상·기록 장치 정상·특정 경로 차단 변경이 확인됐다면 차단을 원인 후보로 좁힌다. 로그가 0이라는 사실만으로 장애를 확정하지 않는다.
4. 기술 담당은 고객이 허용한 수정 범위에서 변경안을 준비하고 검토·배포 절차를 수행한다.
5. 검증 담당은 실제 robots 응답과 대상 URL 접근을 다시 확인한다. 여기까지는 기술 수정 완료다.
6. 방문 재개 여부는 정한 기간 뒤 관찰한다. 크롤러가 다시 왔다고 AI 답변 인용 증가를 주장하지 않는다.
7. 재개되지 않으면 같은 수정이나 색인 요청을 반복하지 않고 남은 가설을 검사한다.

능동성에는 기회 발굴도 포함한다. 예를 들어 경쟁 지면에서 질문 수요를 발견하면 기존 고객 콘텐츠의 공백과 사업 적합성을 조사하고, 우선순위가 높은 경우 근거와 초안을 준비한다. 일을 늘리는 것 자체를 성과로 세지 않는다.

## 운영 화면과 보고

기존 `/admin/ops`의 업무 흐름에 다음 정보를 연결한다.

- 고객 목표별 진행 상태와 최근 측정 시각
- 문제별 담당자, 사업 영향, 확인한 사실, 현재 가설
- 지금 수행하는 작업과 실제 실행 기록
- 다음 행동과 재확인 시각, 사람에게 필요한 결정
- 기술 해결과 성과 관찰 결과

움직이는 화면이나 예정된 시간만으로 작업 중이라고 표시하지 않는다. 실행 기록과 최근 heartbeat로 상태를 보여준다. 변경 없는 경고는 반복 발송하지 않고 상태 변화·중요한 실패·필요한 결정만 알린다.

대표 보고는 “무엇이 문제였고, 무엇을 확인했고, 무엇을 했으며, 결과와 다음 확인은 무엇인가”로 작성한다. 모르는 원인은 모른다고 쓴다.

## 단계별 구현 순서와 통과 기준

### 1. 업무와 근거를 남긴다

정찰 결과를 고객별 업무로 적재하고 담당자·상태·다음 확인 시각을 붙인다. 조회 실패와 0건을 분리한다. 실행 권한은 늘리지 않는다.

통과 기준: 같은 탐지가 중복 업무를 만들지 않고, 조회 실패로 문제가 닫히지 않으며, 고객이 섞이지 않는다.

### 2. 원인을 조사한다

측정 누락·브랜드 미노출·크롤러 단절 세 유형부터 읽기 도구로 조사한다. 실행 계획은 제안 상태로 저장한다.

통과 기준: 정상 무방문·기록 장치 오류·실제 차단의 사례를 구분하고, 근거 부족 시 확인 불가를 반환한다. 최신 하루 0건을 연속 실패로 과장하지 않는다.

### 3. 허용된 작업을 수행한다

재측정, 내부 초안, 승인 범위의 기술 수정부터 연결한다. 외부 반영은 기존 권한·검토 절차를 적용한다.

통과 기준: 중간 종료 후 복구해도 중복 발행·중복 변경이 없고, 권한 밖 자산에 접근하지 않으며, 실행 실패가 성공으로 기록되지 않는다.

### 4. 검증하고 개선한다

후속 측정과 재발 연결을 구현하고 운영 화면에 결과를 표시한다. 검증된 사례를 다음 조사에서 참고한다. 단일 사례만으로 공통 스킬을 자동 변경하지 않는다.

통과 기준: 미검증 작업을 해결 처리하지 않고, 효과가 없는 작업의 반복을 멈추며, 반증에 따라 가설을 바꾼다.

품질 평가는 자동 처리 건수와 함께 오진율, 재발률, 검증된 해결까지 걸린 시간, 업무당 비용, 사람 개입 이유, 고객 목표 개선을 본다. 먼저 기록된 사례로 실행 없이 판단을 평가하고, 제한된 고객·작업에 적용한 뒤 범위를 넓힌다.
